# Task Organization Postman Guide: Remote Supabase

This guide explains how to run the task organization Postman collection against a **dedicated remote Supabase test project**. It assumes you are new to Postman and Supabase. You do not need Docker, and you must not start local Supabase.

## Can I run the collection all at once?

**Yes. This collection runs all 32 task organization requests in one Collection Runner session.** Select the 339 environment and run the collection in its existing order. Login requests and setup requests capture tokens, task IDs, and label IDs automatically. The first login generates a unique `runId` for task and label names, so there are no manual copy/paste steps.

Do not reorder or skip the setup requests. Later requests use IDs generated by earlier requests. You can also send requests individually for troubleshooting, but send them in order.

## Important safety warning

Use a **dedicated, isolated Supabase project for testing**. Do not use production, a teammate's project, or a shared development project. These tests create real tasks and labels, attach/detach labels, and delete some labels. Not all test data is cleaned up.

Never run **supabase db reset --linked** for this guide. It drops and recreates the linked remote database. Use **Supabase: Seed Remote** for shared fixtures; it does not reset the whole database, but does create/update the seeded users and other fixtures.

## Before you begin

You need VS Code, Postman, Node.js 22 or later, and access to a dedicated remote Supabase test project. Docker Desktop is not needed. If repository dependencies are not installed, run **📦 Install All Dependencies** from **Tasks: Run Task**.

## 1. Link and prepare the remote test project

1. Sign in to the Supabase Dashboard and open the dedicated test project. Note its name and project reference. Do not continue if you cannot distinguish it from production or shared development.
2. In VS Code, choose **Terminal > New Terminal**. Confirm that the terminal is at the repository root, the folder containing `package.json` and `supabase`. If needed, enter:

   ```powershell
   cd C:\Users\Matthew\source\repos\project-team-404
   ```

3. Open the Command Palette with `Ctrl+Shift+P`, choose **Tasks: Run Task**, and run **🔐 Supabase: Login**. Follow the browser sign-in steps.
4. Run **🔗 Supabase: Link Project**. Select the dedicated test project and verify its name/reference before confirming. Enter its database password directly into the terminal if prompted; do not put it in Postman or a checked-in file.
5. Run **📊 Supabase: Check Migration Status**. If repository migrations are pending, run **📤 Supabase: Push Migrations**. If the CLI suggests destructive reset/replacement, cancel and confirm with the project owner.
6. Run **🌱 Supabase: Seed Remote**. Each seed file runs against the linked project and reports `SUCCEEDED` or `ERROR` based on SQL execution. Stop if any seed reports `ERROR`.

The seed task is not a full database reset. It sets the seeded users' passwords to `password123` and updates fixtures. Run it only against the dedicated test project.

## 2. Configure the backend

Postman calls the Express API running on your computer. The API connects to the remote test project.

1. In VS Code's Explorer, open `backend/.env`. If it does not exist, run **🛠️ Setup: Create Environment Files** from **Tasks: Run Task**.
2. Set `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, and `DATABASE_URL` to values for the same remote test project. Set `DIRECT_URL` to its direct database URI. Use the Supabase Dashboard values, not the placeholders in `backend/.env.example`.
3. Set or confirm `NODE_ENV=development`, `PORT=3000`, `WEB_APP_URL=http://localhost:4200`, and `CORS_ALLOWED_ORIGINS=http://localhost:4200`.
4. These tests do not send email. If you have no other reason to configure Brevo, remove or comment out `BREVO_API_KEY` and `BREVO_SENDER_EMAIL`. Do not leave empty assignments; the backend rejects supplied empty strings.
5. Save `backend/.env` with `Ctrl+S`. If the backend is already running, stop it with `Ctrl+C`; start it again in the next section.

Keep the service-role key and database URI private in `backend/.env`. Do not put them in the Postman environment. `SUPABASE_TEST_*` variables are for automated test runners, not these manual Postman requests.

## 3. Start the frontend and API

1. In VS Code, press `Ctrl+Shift+P`, choose **Tasks: Run Task**, and select **🚀 Dev: Start All**. This starts the frontend and backend in parallel.
2. Keep the task running while using Postman. Wait for the backend terminal to report that the server is listening on port `3000`; the frontend runs on port `4200`.
3. Open `http://localhost:3000/health` in a browser to confirm that the API is reachable.

## 4. Import the Postman files

This folder contains:

- `Project-Team-404 API - 339-task-organization.postman_collection.json`
- `Project-Team-404 Local (339-task-organization).postman_environment.json`

1. Open Postman and choose your workspace.
2. In Windows File Explorer, open:

   ```text
   C:\Users\Matthew\source\repos\project-team-404\tests\postman\339-task-organization
   ```

3. Select both JSON files: click one, hold `Ctrl`, and click the other.
4. Drag both files into the Postman window and drop them. Confirm the import preview. Alternatively, click **Import**, choose **Files**, select both files, and confirm.
5. Confirm the collection and environment appear as **Project-Team-404 API - 339-task-organization** and **Project-Team-404 Local (339-task-organization)**.

## 5. Select and check the environment

The collection's **Variables** tab may be empty; its requests use the selected environment.

1. Click the environment selector near Postman's upper-right corner and select **Project-Team-404 Local (339-task-organization)**. Confirm it has a check mark under **Environments** in the left sidebar.
2. Check these values in the environment's **Current value** column:

   | Variable | Expected value/action |
   | --- | --- |
   | `baseUrl` | `http://localhost:3000/api` |
   | `token`, `tokenB` | Leave blank; login requests set them. |
   | `runId` | Leave blank; James's login request generates it. |
   | `orgTaskId`, `orgTaskIdB` | Leave blank; task setup requests set them. |
   | `orgLabelId`, `orgLabelIdB`, `orgUnusedLabelId`, `orgCascadeLabelId` | Leave blank; label setup requests set them. |

3. If `baseUrl` differs, set it to `http://localhost:3000/api`. This is the local API address, not the remote Supabase URL.
4. Do not manually fill generated values. Save the environment if Postman shows a **Save** button or unsaved-changes indicator.

## 6. Run all requests in Collection Runner

1. Confirm the backend is running and **Project-Team-404 Local (339-task-organization)** is selected.
2. In the **Collections** sidebar, expand **Project-Team-404 API - 339-task-organization**.
3. Click the collection's **Run** button or choose **Run** from its `...` menu.
4. In Collection Runner, select all 32 requests in the `339-task-organization` folder, keep their existing order, and confirm the 339 environment.
5. Click **Run 339-task-organization** (or the equivalent **Run** button in your Postman version). Wait for the summary.

Some requests are expected to return `400`, `404`, `409`, or `204`. They are intended validation, ownership, or deletion cases; the tests pass when Postman reports their assertions as passed.

### Send requests one at a time for troubleshooting

Expand the collection folder, click a request, and click **Send**. Keep the same environment selected and send requests in order. The first two logins must run before the task setup; task and label setup must run before the requests that use their IDs.

## 8. Data left behind and common failures

Some tasks and labels remain in the remote project after a run. Organization task and label names include the generated `runId`, so they are unique on reruns. This is expected for an isolated test project.

| Postman result | Check this |
| --- | --- |
| Connection refused or no response | Confirm **🚀 Dev: Start All** is running and `baseUrl` is `http://localhost:3000/api`. |
| A seeded login returns `401` | Confirm the remote test project was seeded, the password is `password123`, and `SUPABASE_URL`/`DATABASE_URL` refer to the same project. |
| A request contains an empty task or label ID | Run the earlier login and setup requests in this folder first, in order. |
| Duplicate label conflicts on a rerun | Start from the first request so the collection generates a fresh `runId`. |
| Backend exits after removing Brevo | Remove/comment out Brevo settings instead of leaving empty assignments, then restart the backend. |
| A migration or seed task reports `ERROR` | Stop and inspect the CLI output and linked project. Do not use the destructive remote reset task. |

This collection does not change James's password. It leaves some generated tasks and labels in the dedicated test project; it does not require manual restoration.
